# Перший збір вакансій

Цей проєкт збирає відкриті оголошення для дослідницького кейсу хакатону. Початкове джерело — [ФКЦ ОПК](https://www.fkc-opk.ru/trudoustrojstvo-v-opk/vacancy). Для HH працює локальний `hh_bulk.py` без ключів і кредитів Firecrawl: він отримує HTML через HTTP-клієнт браузерної сесії та розбирає дані через Scrapling. Черга зберігається в SQLite й продовжується після переривання. Раніше через Firecrawl отримано окремий пілот із 10 карток. Адаптер [офіційного API HeadHunter](https://github.com/hhru/api) отримав HTTP 403; цей API-шлях поки не підтверджений.

## HH: локальний збір із продовженням

На цьому комп'ютері встановлено `scrapling[fetchers]==0.4.15` і Chromium у `.browser-cache/`. **Для команд нижче не потрібні Firecrawl API key, Client ID, Client Secret або токен HH.** За замовчуванням `--transport http` отримує початковий HTML без запуску JavaScript сторінки; екранований JSON у `template#HH-Lux-InitialState` розбирається без виконання коду. Для варіанта із виконанням JavaScript можна явно задати `--transport browser`. Автоматичного перемикання після відмови сервера немає. У живому тесті швидкого режиму 10 повних карток і 229 унікальних ID із трьох сторінок пошуку отримано за 13,2 секунди збору (без запуску браузера). Поля однієї картки також порівняні з браузерним HTML: ID, назва, опис, роботодавець, зарплата, навички та секції збіглися. Результат тесту — `tmp/hh_bulk_fast_check/`.

```powershell
# Переглянути план без мережевих запитів
.\.venv\Scripts\python.exe hh_bulk.py

# Зупиніть попередню версію через Ctrl+C перед застосуванням оновлення.
# Розширити стару чергу й продовжити до 1000 повних карток
.\.venv\Scripts\python.exe hh_bulk.py --run --extend-searches --limit 1000 --max-requests 1500 --workers 2 --delay 0.5

# Переглянути збережений результат без нових завантажень
.\.venv\Scripts\python.exe hh_bulk.py --export-only
```

Результат зберігається постійно в **`C:\Users\aleks\Desktop\projects\Парсинг\data\hh_bulk\`**, а не в новій папці кожного запуску. Міграцію перевірено на копії наявної бази з 83 повними картками: усі збережено, додано нові пошуки, старі незавершені пошукові сторінки по 20 результатів замінено пошуками по 100. Завантажені картки не запитуються повторно. `Ctrl+C` зупиняє збір; повторення тієї самої команди продовжує чергу. Запускайте один процес для однієї бази. Ліміт означає загальне число унікальних розібраних карток у базі, включно зі слабкими збігами та відсівом, а не число нових карток за запуск.

`--workers 2` дозволяє два завантаження одночасно. `--delay 0.5` задає спільний інтервал **між початками** запитів, а не додаткову паузу після кожного завантаження. Без цього параметра інтервал — 1 секунда. Дозволено 1–4 паралельні завантаження; мінімальний спільний інтервал — 0,5 секунди. `--discovery-every 5` за замовчуванням віддає перевагу пошуковій сторінці кожного п'ятого запуску запиту; спочатку переглядаються перші сторінки різних фраз. Завдяки цьому список знайдених ID зростає під час завантаження карток. `--max-requests` обмежує загальне число запитів за один запуск, незалежно від числа workers. У режимі `browser` сторінки також завантажують ресурси. CSV/JSONL оновлюються після завершення, помилки або `Ctrl+C`; SQLite поповнюється після кожної успішно розібраної сторінки. У прогресі з'являються `new_cards_this_run`, `in_flight` і `cards_per_minute`; вимірювання зберігається в `manifest.json` як `last_run_metrics`.

| Файл | Що зберігається |
| --- | --- |
| `queue.sqlite3` | Черга, стан кожного запиту, унікальні ID, повні записи та помилки. Основне сховище для продовження. |
| `vacancies.csv`, `vacancies.jsonl` | Кандидати за роботодавцем або сильними текстовими сигналами. |
| `review.*` | Слабкі сигнали для перевірки. |
| `excluded.*` | Відсіяні оголошення з причиною. |
| `full_cards.*` | Усі успішно розібрані картки, включно з перевіркою й відсівом. |
| `index.*` | Усі знайдені оголошення зі списків; частина може ще чекати опису. |
| `discovery_routes.jsonl` | Усі пошукові шляхи для кожного ID, навіть якщо він знайдений кількома запитами. |
| `search_report.jsonl`, `manifest.json` | Покриття пошуків, обмежені сторінки, лічильники та стан запуску. |
| `errors.jsonl` | Запити, які зупинили збір, число спроб і остання помилка. |
| `raw/*.html.gz` | Стиснуті вихідні HTML-знімки та сусідні метадані з SHA-256 нестиснутого HTML. |

Повтори між пошуками не завантажуються вдруге. Черга й результати однієї сторінки фіксуються однією транзакцією. Експорт читає базу поступово, без завантаження всіх карток у оперативну пам'ять. За 401/403/406/429, капчі чи неочікуваної розмітки збір зупиняється, записує помилку й залишає завдання для наступного ручного запуску. Виняток — картка з HTTP 403 і явним повідомленням HH «Вам недоступна эта вакансия» та вимогою входу користувача з доступом: вона позначається `restricted`, а збір продовжується без отримання закритих даних. Загальну відмову 403 парсер не пропускає. Зниклі картки з 404/410 позначаються недоступними; інші завдання залишаються в роботі.

Якщо Windows забороняє замінити відкритий CSV, парсер збереже актуальний файл під назвою на зразок `vacancies_export_<номер>.csv` і продовжить експорт решти файлів. `manifest.json` містить фактичні назви в `export_files` і попередження в `export_warnings`. Основний відкритий CSV може залишитися старим: закрийте його в Excel та виконайте `--export-only`, щоб оновити звичайну назву. SQLite зберігає прогрес незалежно від CSV. Якщо запис неможливий навіть під іншою назвою, скрипт повідомить про незавершений експорт без traceback.

Звичайні HTTP-перенаправлення 301/302/303/307/308 обробляються до чотирьох переходів, тільки для HTTPS-сторінок HH зі збереженням ID вакансії або параметрів пошуку. Посилання на вакансію може вести на рекламну статтю замість картки: такі записи пропускаються зі станом `redirected`, а `index.*` отримує `detail_status=redirected_non_vacancy`. Адреса переходу залишається в метаданих HTML. Такий пропуск не зупиняє решту черги та не додає повну картку до лічильника. Перенаправлення на авторизацію/капчу, цикли або зміна фільтрів пошуку зупиняють збір.

### Якщо HH вимагає капчу

Підтверджений випадок: після 49 нових карток і 957 знайдених ID HH повернув 302 на `/account/captcha`. Причину спрацювання перевірки за цим журналом не встановлено. Це відрізняється від рекламного перенаправлення: парсер зберігає чергу, припиняє завантаження й повідомляє `access_check_required`.

```powershell
# Відкрити окремий видимий браузер у сесії цього парсера
.\.venv\Scripts\python.exe hh_bulk.py --manual-check
```

Пройдіть показану капчу вручну, дочекайтеся сторінки вакансії/пошуку, поверніться в термінал і натисніть Enter. До цього не закривайте відкрите вікно. Команда перевіряє наявність даних вакансії/пошуку й зберігає сесію локально в `data/hh_bulk/browser-profile/session-state.json`. Це файл браузерної сесії, він не потрапляє у CSV/JSONL чи репозиторій. Звичайний браузер Chrome користувача має іншу сесію: проходження перевірки тільки там не означає її проходження для парсера.

Після успішної ручної перевірки продовжіть із нижчою частотою запитів:

```powershell
.\.venv\Scripts\python.exe hh_bulk.py --run --limit 1000 --max-requests 1200 --workers 1 --delay 2
```

Це продовження наявної черги, а не повторний збір готових карток. Частота нижча, але наступна капча все одно можлива. Якщо перевірка залишається у браузері, режим ручної перевірки не повідомлятиме про успішне завершення.

### Нічний режим без діалогів

```powershell
.\.venv\Scripts\python.exe hh_bulk.py --overnight --hours 8 --limit 5000 --max-requests 10000
```

Потрібно залишити термінал і комп'ютер увімкненими. Режим використовує один потік та інтервал не менше 3 секунд між початками запитів. Черга фіксується після кожної сторінки, CSV/JSONL експортуються кожні 100 успішних завдань і після завершення. Час роботи обмежено 8 годинами (параметр `--hours`); 5000 — загальна межа повних карток у базі, а не гарантований результат за ніч.

При вимозі капчі режим зберігає результат, чекає 30 хвилин, потім перевіряє тільки заблокований запит тією самою сесією. Якщо HH знову віддає публічні дані, черга продовжується. Після трьох невдалих перевірок робота завершується зі статусом `access_check_required`. Якщо капча вже записана в журналі перед запуском, очікування починається відразу, без нового масового збору. Параметри: `--cooldown-minutes 30`, `--max-access-checks 3`.

Капча не розв'язується автоматично, сесії/проксі не підміняються. Нічний режим не потребує ручного вводу, але не може гарантувати доступ, якщо HH зберігає вимогу перевірки. Події записуються в `data/hh_bulk/night_events.jsonl`, підсумок — у `manifest.json` (`night_run`). Загальний ліміт запитів діє також на перевірки після очікування.

**Обсяг.** Збираємо кандидатів ВПК: два роботодавці та **57 фраз** із `hh_config.json`, разом 59 пошуків. Нові групи фраз: ГОЗ/275-ФЗ/воєнні представництва; оборонна продукція, боєприпаси, ракетна й бронетехніка; БПЛА та безпілотні авіаційні системи; РЕБ і радіолокація; назви оборонних холдингів та підприємств. Не додаються загальні професії на кшталт «токар» чи «бухгалтер» для всіх роботодавців. Назви холдингів у тексті не замінюють перевірений HH ID роботодавця.

Слабкі та подвійні за призначенням ознаки (дрони, радіолокація, спеціальна техніка, згадка бренду) зберігаються в `review.*`. Це може бути цивільна діяльність. Сильні ознаки ведуть у `vacancies.*`, але статус ВПК все одно `unverified`. Додано фільтри явно названого військового контрактного найму, включно з «Оператор БПЛА (СВО)». Нові правила застосовуються і до вже збережених карток під час розширення черги.

Сторінка тепер запитує 100 оголошень; у живому тесті HH повернув усі 100. За замовчуванням допускається до 100 сторінок на кожен пошук. Якщо ще є наступна сторінка, але досягнуто нашої межі, пошук отримує стан `capped`. Якщо HH закінчив пагінацію раніше повідомленого числа результатів, ставиться `incomplete`. У наявному старому знімку HH повідомляв 4256 результатів для «оборонное предприятие» й 2896 для «оборонно-промышленный»; на той момент було отримано лише їхні перші сторінки. Ці числа містять перетини, не є числом підтверджених військових вакансій і можуть змінюватися. Повтори за ID не збираються вдруге. **Саме збільшення `--limit` до 100000 не гарантує такого обсягу**: після вичерпання доступних пошуків процес завершується. Для пошуків з неповним покриттям знадобиться подальше розбиття за регіонами або роботодавцями.

Збирач приймає великий ліміт, наприклад:

```powershell
.\.venv\Scripts\python.exe hh_bulk.py --run --extend-searches --limit 100000 --max-requests 110000 --workers 2 --delay 1
```

Підтверджено короткий живий запуск і перевірки черги, а не безперервний збір 100 000 карток. Кредити Firecrawl та OpenAI для роботи цього скрипта не витрачаються; потрібні інтернет, місце на диску й час роботи комп'ютера. У тесті з інтервалом 1 секунда швидкість склала близько 45 повних карток на хвилину з урахуванням запитів списків. Подальше продовження з інтервалом 0,5 секунди отримало **20 нових повних карток за 12 секунд**, близько 100 на хвилину, без повторного завантаження перших десяти. Другий тест містив лише готову чергу карток, без нових списків; обидва вимірювання виключають запуск браузера й фінальний експорт. Усього в `tmp/hh_bulk_fast_check/` 30 карток і 229 унікальних ID. Орієнтир для 1000 нових карток у швидкому режимі — приблизно 10–20 хвилин за подібних умов. При спільному інтервалі 0,5 секунди тільки запуск 100 000 запитів потребує щонайменше близько 14 годин; час залежить також від затримок, доступу, повторів у списках і кількості доступних кандидатів. Точнішу оцінку робіть після 500–1000 завантажень за `cards_per_minute`.

Набір полів береться з `output_fields` у `hh_config.json`: назва, роботодавець і його HH ID, посилання, дата публікації/спостереження, регіон, адреса, зарплата, опис, обов'язки, вимоги, умови, навички, графік та докази фільтра. Пропущені поля залишаються порожніми. `--extend-searches` дозволяє лише додавати фрази, роботодавців, правила та збільшувати розмір сторінки зі збереженням карток. Він перевіряє первинний конфіг за SHA-256, повторно класифікує готові записи без мережі й фіксує зміну транзакцією. Видалення/заміна попередніх правил, зміна регіонів, колонок або `--pages` потребують нової папки через `--output data\hh_bulk_v2`. Повторний запуск із тим самим `--extend-searches` безпечний і не додає дублікати. Для регулярного оновлення завершеного збору також створіть нову папку; режим продовження не оновлює вже готові картки.

На новому комп'ютері після встановлення залежностей:

```powershell
$env:PLAYWRIGHT_BROWSERS_PATH = Join-Path (Get-Location) '.browser-cache'
.\.venv\Scripts\python.exe -m playwright install chromium
```

Перевірки без мережі: `.\.venv\Scripts\python.exe -m unittest discover -s tests -q`.

## Що означає «парсинг»

1. **Завантаження:** скрипт звертається до сайту й отримує HTML або JSON.
2. **Розбір:** з відповіді виділяються назва вакансії, роботодавець, опис та інші поля.
3. **Нормалізація:** різні назви полів джерела перетворюються на одну схему.
4. **Збереження:** оригінальні відповіді залишаються в `raw`, очищені записи — у CSV і JSONL.

HTML — розмітка сторінки. CSS-селектор — правило вибору елемента, наприклад `title::text` бере текст заголовка сторінки. JSON — уже структурована відповідь із полями; для неї селектори не потрібні. API — інтерфейс отримання таких даних програмою.

**ФКЦ ОПК:** сторінка спочатку показує «Загрузка…», а JavaScript окремо завантажує список. Збирач повторює саме ці публічні запити до списку та картки; браузер запускати не потрібно. POST до списку тут тільки читає дані. Збирач не звертається до функцій відгуку, надсилання резюме чи зміни вакансій.

**HeadHunter:** офіційний API повертає сторінки результатів. Після списку треба запитати деталі кожної вакансії, щоб отримати повний опис. Одна сторінка пошуку не є всією базою РФ.

## Початок на цьому комп'ютері

Віртуальне середовище `.venv` уже підготовлено, Scrapling 0.4.15 встановлено. Працюйте з термінала PowerShell у цій папці. Активувати середовище не потрібно.

Перевірений результат першого запуску 4 жовтня 2026: `data/fkc_index/` — 735 оголошень і 161 різна назва роботодавця зі списку; `data/fkc_pilot/` — 20 повних карток із 5 назвами роботодавців. Пілот зайняв близько 31 секунди. Перевірені відповідність полів вихідним карткам, унікальність ID, хеші оригіналів і кількість рядків CSV. Це не 161 підтверджене підприємство ВПК: юридичні особи та статус ще потрібно перевіряти.

```powershell
# Допомога з усіма параметрами
.\.venv\Scripts\python.exe collect.py --help

# 20 вакансій із повними описами; кожен запуск створює нову папку
.\.venv\Scripts\python.exe collect.py fkc --limit 20 --details

# Увесь список, але без окремого завантаження описів
.\.venv\Scripts\python.exe collect.py fkc --limit 0

# Наступна вибірка з 50 описами
.\.venv\Scripts\python.exe collect.py fkc --limit 50 --details
```

Новий комп'ютер: потрібні Python 3.10+ та `uv`. Створіть середовище й установіть залежності:

```powershell
uv venv --python 3.12 .venv
uv pip install --python .venv\Scripts\python.exe -r requirements.txt
```

Команда створення середовища може завантажити Python, якщо відповідної версії немає. Повторно створювати вже підготовлене середовище не потрібно.

## Файли результату

Пілотні збирачі `collect.py` та `hh_web.py` створюють окрему папку `data/<джерело>_<час UTC>/`. Для `hh_bulk.py` використовується постійна папка, описана вище:

| Файл | Призначення |
| --- | --- |
| `vacancies.csv` | Перегляд в Excel. UTF-8 із BOM, текст захищений від виконання як формула. |
| `vacancies.jsonl` | Дані для NLP і завантаження в базу; один JSON-запис на рядок. |
| `employers.csv` | Кількість зібраних оголошень за назвами роботодавців. |
| `manifest.json` | Параметри, час, кількість записів, помилки, хеші оригінальних відповідей. |
| `raw/` | HTML сторінки та вихідні JSON-відповіді списку й карток. |

`employers.csv` групує назви в межах джерела: це ще не реєстр унікальних юридичних осіб. Наприклад, бренд і юридична назва можуть відрізнятися. `employer_source_id` належить платформі, не є ІПН/ІНН. `collected_postings` — число оголошень у вибірці, а не число працівників чи всі вакансії підприємства.

## Поля та обмеження

- `employer_name` — назва зі списку; `employer_name_detail` — назва з картки. Зберігаємо обидві.
- `title`, `responsibilities`, `requirements`, `conditions`, `skills` — тексти для майбутнього NLP.
- `industry_label_source` — дослівна галузева мітка джерела. Вона може бути «Нет в реестре Минпромторга»; це не висновок нашої системи.
- `source_url`, `detail_url`, `observed_at` — походження та час спостереження.
- `published_at_source` зберігає дату так, як її віддав сайт. Часовий пояс джерела не встановлений. Час збору — UTC.
- `vpk_status` поки `unverified`: публікація на порталі ОПК або збіг пошукового слова не доводять військової діяльності юридичної особи.
- `source_visibility` означає наявність у відкритому списку під час збору. Давнє оголошення може бути неактуальним.
- Адреса не позначається як виробничий об'єкт, якщо джерело цього не встановлює.
- Публічні ділові контакти з оголошення зберігаються окремо. Контакти кандидатів не збираються.
- Пропущені дані залишаються порожніми. Для FKC період зарплати та значення «до/після податків» не визначаємо самостійно.

У пілотному `collect.py` затримка між деталями за замовчуванням — 1 секунда. Є тайм-аут та одна повторна спроба для тимчасових мережевих помилок. При 401/403/429 збір зупиняється. Після помилки перевіряйте `manifest.json`; код завершення буде ненульовим. Сам `collect.py` не продовжує перервані збори; для HH продовження реалізовано в `hh_bulk.py`.

## Робочий шлях HH: відкриті HTML-сторінки

`hh_web.py` отримує сторінку `https://hh.ru/search/vacancy?...`, виділяє ID оголошень, завантажує `https://hh.ru/vacancy/<ID>` і розбирає публічний стан сторінки через `json` та Scrapling. Це окремий шлях від `api.hh.ru`: для нього не потрібні Client ID, Client Secret або токен HH. Повні описи перевірені також проти JSON-LD `JobPosting` у HTML.

Підтверджений пілот 4 жовтня 2026: `data/hh_html_pilot_10/` — 10 повних кандидатів із 8 назвами роботодавців; `index.*` — 22 унікальні оголошення зі списків. Пошук «гособоронзаказ» показував 229 результатів, але завантажена лише перша сторінка з 20. Для профілю Ростеху список містив 2 оголошення. Вибірка не є всією базою HH або переліком підтверджених підприємств ВПК. Серед кандидатів є Банк ПСБ та ІСП РАН: текстовий збіг може показувати обслуговування ГОЗ, а не виробництво військової продукції.

Джерелом пілоту були 12 свіжих відповідей Firecrawl (2 списки та 10 карток), кожна зі статусом 200, `maxAge=0`, проксі `basic`. Для цих завантажень HH метадані повідомили сумарно 12 кредитів; дослідницькі запити до документації оплачуються окремо за правилами сервісу. Прямий запит Python до відкритого списку отримав HTTP 406. Автоматичного обходу капчі, зміни проксі чи повторення відмов тут немає.

Команди нижче можна запускати як у CMD, так і в PowerShell:

```bat
REM Повторно розібрати вже збережені сторінки: без інтернету й нових кредитів
.\.venv\Scripts\python.exe hh_web.py --snapshots data\hh_web_pilot\raw

REM Подивитися план нового збору: також без HTTP-запитів
.\.venv\Scripts\python.exe hh_web.py --query "гособоронзаказ" --limit 10

REM Новий збір через Firecrawl: запитує його власний API-ключ приховано
.\.venv\Scripts\python.exe hh_web.py --run --query "гособоронзаказ" --limit 10 --ask-firecrawl-key
```

У самостійному запуску Python ключ береться з `FIRECRAWL_API_KEY` або прихованого вводу `--ask-firecrawl-key`. Це ключ Firecrawl, а не HH; він не записується на диск. Підключений MCP-плагін у Codex уже виконав завантаження пілоту через свою авторизацію. Локальний скрипт автоматично не отримує доступ до секретів цього плагіна. Збір через REST Firecrawl реалізований за [офіційним контрактом](https://docs.firecrawl.dev/api-reference/endpoint/scrape), перевірений на синтетичних відповідях; живий REST-запуск із власним API-ключем користувача поки не виконувався.

Нові результати й оригінали записуються у `data/hh_html_<час UTC>/`; наявні папки не перезаписуються. `vacancies.*` містить повні картки кандидатів, `review.*` — слабкі сигнали, `excluded.*` — відсів, `index.*` — окремий список оголошень зі статусом `pending_details`, якщо для них не отримано повну картку. Індекс не замінює описів для NLP. `manifest.json` містить обсяг, помилки, пагінацію та хеші джерел.

Повні картки містять назву, ID і URL вакансії, назву й ID профілю роботодавця, дату, регіон, адресу вакансії, зарплату та ознаку податків, період зарплати, досвід, графік, повний опис, явно позначені обов'язки/вимоги/умови й навички. Приховані контакти та службові ID менеджерів не експортуються; пропущені поля залишаються порожніми. Адреса вакансії не оголошується адресою виробничого об'єкта.

Правила беруться з того ж `hh_config.json`. За замовчуванням новий збір обмежений 10 повними картками, однією сторінкою на пошук і паузою 2 секунди. `--limit` рахує також картки для перевірки та відсіву. Без `--query` використовуються всі налаштовані маршрути, спочатку роботодавці. Для HTML дата `date_from/date_to` поки не підтримується: живий запуск із такими полями явно відхиляється. Режим `--snapshots` розбирає всі збережені картки, незалежно від лімітів нового завантаження. HTTP-відмова або неочікувана структура зупиняє новий збір зі збереженням уже отриманих результатів.

## Адаптер офіційного API HeadHunter

Налаштування винесено в `hh_config.json`: 10 пошукових фраз, РФ (`area=113`), два початкові профілі роботодавців, правила відбору та атрибути. Це стартовий список, а не всі підприємства ВПК.

**HH за замовчуванням працює в dry-run:** друкує план і не робить HTTP-запитів, не створює вибірку. Для збору після перегляду налаштувань потрібен явний прапорець `--run`. Під час налаштування HH збір не запускався, тести використовували лише вигадані записи.

```powershell
# Переглянути весь налаштований план без збору
.\.venv\Scripts\python.exe collect.py hh --dry-run

# Переглянути окремий пошук без збору
.\.venv\Scripts\python.exe collect.py hh --query "гособоронзаказ" --dry-run

# Переглянути пошук усіх професій у конкретного роботодавця без збору
.\.venv\Scripts\python.exe collect.py hh --employer-id 219911 --dry-run
```

Налаштовані два шляхи виявлення: всі професії у роботодавців зі стартового списку та текстові ознаки ОПК/ГОЗ/військової прийомки. БПЛА й інші слабкі ознаки ведуть до окремої перевірки: вони можуть стосуватися цивільної діяльності. Згадки конфіденційності чи звичайних виробничих професій самі по собі не є сигналом ВПК. Вакансії військової служби виключаються за назвою; текст опису не відкидається лише через згадку військовослужбовців.

Після майбутнього запуску: `vacancies.*` міститиме кандидатів за роботодавцем або сильними сигналами; `review.*` — слабкі збіги; `excluded.*` — виключені оголошення з причиною. Повтори за ID HH не завантажуються двічі. Статус `vpk_status` залишається `unverified`: правила відбору не доводять військової діяльності юридичної особи й не встановлюють кінцевого роботодавця за кадровою агенцією.

Стартові обмеження: 20 оголошень на сторінку, максимум 2 сторінки на пошук, 100 спроб отримання унікальних карток загалом, пауза 1 секунда. `max_details` рахує всі картки, включно з перевіркою й відсівом, а не лише прийняті записи. При досягненні ліміту частина наступних пошуків може не виконатися; це відображається в журналі. `date_from` і `date_to` поки порожні. `output_fields` визначає колонки; основні поля походження й рішення фільтра мають залишатися.

До отримання успішної відповіді не використовуйте HH як підтверджено працююче джерело. При 403 або тайм-ауті зберігається журнал; порожній результат не означає відсутності вакансій. `area=113` обмежує пошук РФ. Загальний збір потребуватиме розбиття пошуку, дотримання лімітів і перевірки дублікатів.

### Якщо HH повернув 403

Команда виконалася, але сервер відмовив у доступі. Нуль записів у цьому випадку не означає, що вакансій немає. Самого коду 403 недостатньо для встановлення причини: потрібен текст відповіді сервера.

```powershell
# Один запит до першого налаштованого пошуку; без повторів, карток і експорту вакансій
.\.venv\Scripts\python.exe collect.py hh --check-access
```

Перевірка створює нову папку `data/hh_check_<час UTC>/` з `manifest.json`. За HTTP-помилки також зберігається `raw/access_check.json.error.json` з відповіддю сервера (до 64 КіБ). У терміналі та журналі видно `http_status`, `server_errors`, підказку та шлях діагностики. Звичайний збір теж тепер зберігає пояснення HTTP-помилок. Старі результати залишаються у своїх папках.

`captcha_required` означає вимогу капчі; помилки типу `oauth` стосуються авторизації. Якщо сервер віддає лише HTML або загальне повідомлення, точна причина залишається невстановленою. Скрипт не повторює відмову 403. Успішна перевірка підтверджує тільки доступність цього пошуку зараз, а не успішність усього збору.

Якщо відповідь містить лише `errors: [{"type": "forbidden"}]`, її недостатньо для встановлення точної причини. Поточний запуск без `HH_ACCESS_TOKEN` анонімний. Підтримка авторизації в скрипті не означає, що HH видасть доступ для цього проєкту.

**Уточнення щодо реєстрації, 4 жовтня 2026.** У формі, яку відкрив користувач, є тільки варіанти користування працівниками одного або кількох роботодавців; вона повідомляє про припинення підтримки API для шукачів роботи з 15 грудня 2025. Команда хакатону, яка досліджує вакансії, не стає роботодавцем через створення акаунта. Перед заявкою потрібно уточнити у HH можливість доступу саме для дослідницького сценарію, включно з NLP та показом результатів на сторонньому сайті. [Умови API](https://dev.hh.ru/admin/developer_agreement), зокрема пункти 4.3, 4.5 та 4.6, містять обмеження щодо створення іншої бази даних для третіх осіб, цілей використання та передачі даних стороннім сервісам. Звичайна реєстрація застосунку не гарантує вирішення цих питань. Для демонстрації вже доступні зібрані набори FKC і Роствертолу; нові запити тут автоматично не запускаються.

Якщо HH погодить заявлений сценарій і видасть доступ, отримайте `access_token` за [офіційною процедурою](https://api.hh.ru/openapi/redoc#tag/Avtorizaciya-prilozheniya). Наявність токена не гарантує доступу до всіх методів; доступ залежить від дозволів застосунку та рішення HH. Наведені нижче команди стосуються цього випадку.

Скрипт тепер підтримує змінну середовища `HH_ACCESS_TOKEN`. Задайте її у своєму PowerShell перед `--check-access`. Для вводу без відображення токена та без його запису в історію команд:

Якщо термінал показує `C:\...>` без префікса `PS`, це CMD. Код із `Read-Host` у ньому не працює. Для отримання нового токена з `Client ID` і `Client Secret` запустіть із CMD один рядок:

```bat
powershell -NoExit -ExecutionPolicy Bypass -File .\get_hh_token.ps1
```

Ця команда відкриває PowerShell у тому самому терміналі й запускає локальний файл. `ExecutionPolicy Bypass` діє лише в цьому процесі. Скрипт запитує ID, прихований секрет і контактну пошту, робить один запит токена, зберігає токен у змінній середовища цього процесу. `-NoExit` залишає його відкритим: наступний `--check-access` потрібно виконати саме тут, де буде префікс `PS`. Збір вакансій автоматично не запускається. При помилці виводиться лише HTTP-статус, без секретної відповіді.

Якщо `access_token` уже отримано, вставте його в PowerShell таким способом:

```powershell
$hhSecret = Read-Host 'HH access_token' -AsSecureString
$env:HH_ACCESS_TOKEN = [System.Net.NetworkCredential]::new('', $hhSecret).Password
.\.venv\Scripts\python.exe collect.py hh --check-access
```

Токен діє в цьому терміналі та його дочірніх процесах. Він надсилається тільки на `https://api.hh.ru` у заголовку `Authorization: Bearer ...`, не переноситься в перенаправлені запити й не записується в конфігурацію або журнал. Відповідь HTTP-помилки очищується від точного значення токена, якщо сервер його відобразив. Журнал показує лише `hh_access_token_configured: true/false`, а не перевірені права доступу. Токен не вставляйте в чат чи `hh_config.json`. Після роботи видаліть змінну: `Remove-Item Env:HH_ACCESS_TOKEN -ErrorAction SilentlyContinue`.

Якщо перевірка з дійсним токеном знову повертає `forbidden`, не повторюйте збір: передайте підтримці HH `request_id` із журналу та уточніть доступність потрібних методів для вашого застосунку. Реєстрацію й видачу доступу не можна замінити локальним налаштуванням скрипта. Успішний живий збір HH поки не підтверджений.

HH просить назву застосунку й контактну пошту в `User-Agent` ([документація](https://api.hh.ru/openapi/redoc#section/Obshaya-informaciya/Trebovaniya-k-zaprosam)). Власне значення можна задати локально в PowerShell: `$env:HH_USER_AGENT = 'VacancyResearchPilot/0.1 (ваша-дійсна-пошта)'`. Укажіть справжню контактну адресу. Це змінює ідентифікацію клієнта, але саме по собі не гарантує усунення 403. Токени або паролі не надсилайте в чат.

## Де тут Scrapling, MCP і Firecrawl

[Scrapling](https://github.com/D4Vinci/Scrapling) — Python-бібліотека. Тут установлено її движок розбору HTML та залежності `fetchers`. `hh_bulk.py` використовує `AsyncDynamicSession` зі звичайним Chromium і повторно використовує сесію протягом запуску: HTTP-клієнт для початкового HTML або паралельні вкладки для браузерного режиму. FKC та офіційний API-адаптер використовують стандартні HTTP-запити Python; HTML-тексти очищує `Selector`, JSON розбирає `json`.

Базове `pip install scrapling` саме по собі не встановлює браузери чи MCP. Браузер для локального HH-збирача вже встановлено; окремий MCP-сервер для запуску Python-файлу не потрібний.

[MCP-сервер Scrapling](https://scrapling.readthedocs.io/en/latest/ai/mcp-server.html) дозволяє агенту викликати інструменти отримання сторінок. Він не замінює схему даних, перевірку фактів, об'єднання компаній чи модель NLP. MCP тут ще не підключений.

Для необов'язкового підключення локального MCP:

```powershell
uv pip install --python .venv\Scripts\python.exe "scrapling[ai]==0.4.15"
# Якщо встановлений Codex CLI:
codex mcp add scrapling -- "C:\Users\aleks\Desktop\projects\Парсинг\.venv\Scripts\scrapling-mcp.exe"
codex mcp list
```

Офіційна документація: [MCP у Codex](https://learn.chatgpt.com/docs/extend/mcp?surface=cli). Альтернативна конфігурація для перегляду — `scrapling-mcp.example.toml`; вона не застосована автоматично. Браузерні інструменти MCP потребують окремої установки браузерних залежностей (`scrapling install`).

Firecrawl підключений. Через його MCP виконано один живий запит до `https://rabota-rostvertol.ru/` із `maxAge=0`. Отримано HTTP 200, HTML і текст сторінки. За метаданими запит використав 1 кредит і звичайний `basic` proxy. Початковий збір ФКЦ ОПК виконаний локальним скриптом без Firecrawl.

Збережений HTML: `data/rostvertol_firecrawl/raw/page.html`. Із нього скрипт `parse_rostvertol.py` через Scrapling виділив **70 карток**, на які посилається список вакансій. В HTML є 144 блоки popup, але непов'язані зі списком блоки не включено. Усі 70 карток мають опис. Результат: `data/rostvertol_pilot/vacancies.csv` та `vacancies.jsonl`.

```powershell
# Повторити розбір уже збереженої сторінки, без мережевого запиту та кредитів
.\.venv\Scripts\python.exe parse_rostvertol.py
```

Це повторний розбір знімка, не оновлення даних із сайту. Для свіжої вибірки спочатку потрібно отримати новий HTML через Firecrawl або інший доступний спосіб. При повторному запуску створюється нова папка. Опис зберігається повністю; зарплата, обов'язки й вимоги на цьому етапі не розділені на поля автоматично. Дата публікації не заповнена, якщо її немає в картці. Під час об'єднання з ФКЦ треба окремо перевірити дублікати вакансій.

## Що робити після пілота

1. Вручну перевірити 20–50 записів проти джерела: назву, опис, зарплату, компанію.
2. Зібрати список підприємств із доказами їхнього статусу, брендами й юридичними ідентифікаторами.
3. Відокремити кадрові агентства від кінцевих роботодавців та прибрати дублікати між джерелами.
4. Додати класифікацію галузі та навичок. Для прихованого роботодавця повертати кандидатів, докази та «невстановлено».
5. Після контролю якості робити картки, карту й аналітику. Рейтинг важливості потребує окремої методології.

Оцінки часу залежать від доступу та розміру команди: ще 1–3 години на перевірку пілота, 1–2 дні на 2–3 джерела, 2–4 дні на базовий NLP та зіставлення, 1–2 дні на простий інтерфейс. Частину роботи команда може робити паралельно. Це оцінки, а не гарантії повноти чи точності.
